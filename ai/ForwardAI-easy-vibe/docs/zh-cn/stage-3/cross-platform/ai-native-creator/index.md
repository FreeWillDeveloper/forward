# 从开发一个网页，到真正的程序，再到 AI 原生创作者

很多人的 Vibe Coding 起点，是让 AI 做一个网页。

你描述想要的样子，AI 写出 HTML、CSS 和 JavaScript。几分钟后，浏览器里出现标题、卡片、动画和按钮。它能被部署成链接，也能分享给别人。这一刻非常重要：你第一次把脑海里的想法变成了可以看见、可以点击的东西。

但做出网页不等于做出了一个可以长期使用的程序；给程序接上一个大模型接口，也不等于做出了 AI 原生产品。

真正的成长会经历三次不同的创造：

> 做出一个页面 → 构建一个可靠系统 → 创造一个能理解目标、调用工具并与人协作的 AI 原生产品

这不是“初级技术到高级技术”的排行榜。网页本身也可以是复杂程序，AI 产品也可能只有一个简单界面。这里讨论的是你承担的责任如何变化：先对画面负责，再对完整任务负责，最后对一个包含不确定智能的结果负责。

## 1. 三个阶段到底差在哪里

| 阶段 | 用户在做什么 | 你主要创造什么 | 成功标准 |
| --- | --- | --- | --- |
| 一个网页 | 浏览、阅读、点击 | 页面、内容和交互 | 别人能打开，并理解你想表达什么 |
| 真正的程序 | 输入、保存、协作、完成任务 | 前后端、数据和稳定流程 | 用户离开你的电脑后仍能可靠使用 |
| AI 原生产品 | 表达目标、授权行动、检查结果 | 模型、上下文、工具和人机协作系统 | AI 能在边界内持续交付有用、可验证的结果 |

对应的创作者角色也在变化：

```text
页面制作者
  关心：它看起来怎样、能否被打开
        ↓
程序开发者
  关心：数据怎样流动、失败怎样恢复、用户怎样完成任务
        ↓
AI 原生创作者
  关心：AI 知道什么、可以做什么、何时询问人、怎样判断结果好坏
```

每一次跃迁都不是抛弃上一层。AI 原生产品仍然需要清晰的页面和可靠的程序，只是在它们之上增加了一种新的能力：让软件不只执行固定按钮，还能理解目标并选择完成目标的路径。

## 2. 第一站：做出一个能分享的网页

网页是最好的创造起点之一，因为反馈非常直接。

你改一句提示词或一段代码，刷新浏览器就能看到结果。你会自然接触到：

- HTML 怎样组织标题、表单、图片和按钮；
- CSS 怎样决定布局、颜色、响应式和视觉层级；
- JavaScript 怎样响应点击、输入和页面状态；
- 浏览器怎样加载资源、调用接口和保存少量本地数据；
- Git 怎样记录变化；
- 部署平台怎样把本地文件变成公开链接。

第一阶段可以做个人主页、活动页、作品集、数据展示、产品落地页或一个小型交互 Demo。

### 一个网页什么时候算完成

不是“在我的电脑上看起来没问题”，而是：

- 陌生人打开链接后知道页面是做什么的；
- 手机和电脑上都能正常阅读和操作；
- 按钮、表单和链接没有虚假入口；
- 图片和字体拥有可使用的来源；
- 页面刷新和直接访问子路径不会报错；
- 没有把 API Key、密码或私人数据写进前端代码；
- 你能修改内容，并重新部署一个新版本。

如果你还没有完整做过这一阶段，可以先完成[现代产品落地页实战](/zh-cn/stage-2/assignments/modern-landing-page/)。

## 3. 漂亮页面为什么还不一定是程序

页面可以演示一个想法，但真实用户会做出 Demo 没有准备过的动作：

- 注册后换一台设备登录；
- 输入空内容、超长内容或错误格式；
- 上传大文件时突然断网；
- 连续点击两次付款；
- 两个人同时修改同一份数据；
- 忘记密码，或者要求注销账号；
- 更新到新版本后继续读取旧数据；
- 在服务器故障时联系客服。

很多“看起来像 App”的页面，内部仍然只是演示：数据写死在代码里，刷新后全部消失；登录按钮没有真正的身份系统；AI 密钥暴露在浏览器；支付只弹出一句“付款成功”；后台地址仍然是 `localhost`。

它不是失败的作品，而是一个原型。原型的任务是证明方向和交互，程序的任务是让真实用户在真实环境中完成事情。

::: tip “真正的程序”不是指一定要安装
一个网站、小程序、手机 App、桌面客户端或命令行工具，都可以是真正的程序。关键不在外壳，而在它是否拥有完整的数据、业务、失败处理、发布和维护闭环。
:::

## 4. 第二站：把页面变成真正的程序

程序的核心不是页面数量，而是一条可以反复完成的任务链路。

以“冰箱大厨”为例：

```text
网页原型
输入食材 → 展示一份预设菜谱

真正的程序
注册或匿名进入 → 提交食材 → 后端生成菜谱
→ 校验结果 → 保存历史 → 换设备后继续查看
→ 出错时重试 → 用户可以删除自己的数据
```

为了支撑这条链路，系统通常会出现这些部分：

```text
用户界面
  ↓ HTTPS
业务 API ── 身份与权限
  ↓
业务逻辑 ── 第三方服务 / 支付 / AI 模型
  ↓
数据库与文件存储
  ↓
日志、监控、备份与告警
```

### 4.1 数据不再跟着页面消失

你需要决定哪些状态只属于当前页面，哪些数据应该保存在设备上，哪些数据必须进入服务器数据库。

真正的程序要回答：

- 谁创建了这条数据？
- 谁可以读取、修改和删除它？
- 两次修改冲突时保留哪一次？
- 数据结构升级时怎样兼容旧记录？
- 用户注销后哪些数据需要删除或保留？
- 备份是否真的能够恢复？

相关教程：[使用 Supabase 构建数据库](/zh-cn/stage-2/backend/database-supabase/)。

### 4.2 机密必须留在服务端

浏览器、手机安装包和桌面客户端最终都运行在用户设备上，不能用来保存组织共享密钥。

正确的调用链路通常是：

```text
客户端 → 自己的业务后端 → 模型 / 支付 / 第三方服务
```

后端负责验证用户、限制调用、保护密钥、记录成本和过滤返回内容。相关教程：[实现安全的 AI 接口](/zh-cn/stage-2/backend/ai-interface-code/)。

### 4.3 正常路径之外也必须成立

Demo 展示成功时的画面，程序还要处理失败：

- 网络超时能否重新尝试；
- 重复提交会不会产生两笔订单；
- 第三方接口返回错误格式会不会导致崩溃；
- 文件上传到一半能否取消；
- 用户权限不足时是否给出清楚说明；
- 服务故障时是否有日志和告警；
- 新版本出问题时是否可以回滚。

错误提示不是开发完成后补上的文案，而是程序行为的一部分。

### 4.4 程序需要离开开发环境

当别人不连接你的电脑，也能安装、打开、升级和获得支持，程序才真正进入现实世界。

它可能发布成：

- 一个公开访问的网站或 PWA；
- 微信小程序；
- Android 或 iOS App；
- Windows、macOS 或 Linux 桌面软件；
- 浏览器、VS Code 插件或命令行工具；
- 企业内部系统和设备客户端。

先根据用户的工作场景阅读[应用应该做成什么平台](../choose-platform/)，完成后再按照[如何把开发好的程序发布上架](../app-publishing/)处理签名、审核、隐私和更新。

## 5. 一个真正的程序怎样算完成

可以用这张清单判断自己是否已经跨过第二阶段：

- [ ] 用户能独立完成一条端到端任务，而不是观看演示；
- [ ] 数据能够正确保存、读取、修改和删除；
- [ ] 身份、角色和数据权限在服务端受到检查；
- [ ] 客户端中没有共享密钥和管理员凭据；
- [ ] 空输入、断网、超时和重复操作都有处理；
- [ ] 在干净设备和 Release 环境中测试过；
- [ ] 有日志、错误监控、备份与恢复方式；
- [ ] 有清晰的版本、发布和回滚流程；
- [ ] 用户知道怎样获得帮助和删除账号；
- [ ] 产品能够在开发者不在场时继续提供服务。

完成这些工作后，你不再只是“用 AI 生成了代码”，而是在设计和维护一个系统。

## 6. 第三站：什么是 AI 原生产品

传统软件把大多数路径提前写死：用户点击 A，程序执行 B，最后显示 C。

AI 原生产品允许用户先表达目标，再由系统结合上下文选择路径：

```text
用户目标
  ↓
理解上下文与约束
  ↓
模型规划下一步
  ↓
调用搜索、数据库、代码、日历或业务 API
  ↓
检查工具结果并继续
  ↓
在关键节点请人确认
  ↓
交付结果并记录反馈
```

这里的 AI 不是页面右下角多出来的聊天气泡，而是产品完成核心任务的组成部分。

### 给程序接入模型，不一定是 AI 原生

| 只是加入 AI 功能 | 更接近 AI 原生 |
| --- | --- |
| 所有页面都放一个通用聊天框 | 交互围绕用户要完成的目标设计 |
| 把一句输入直接转发给模型 | 组合用户、业务、历史和实时上下文 |
| 模型只生成一段文字 | 模型可以调用受控工具并改变业务状态 |
| 只设计成功示例 | 处理幻觉、拒答、超时和工具失败 |
| 输出后立即执行 | 高风险操作先预览并让用户确认 |
| 凭感觉判断效果 | 用测试集、用户反馈和指标持续评估 |
| 只关心回答看起来聪明 | 同时控制正确性、延迟、成本和安全 |

AI 原生并不要求所有事情都交给模型。恰恰相反，优秀的产品会把确定性工作交给普通代码，把需要理解、生成和判断的部分交给模型，再用规则、权限和人工确认限制风险。

## 7. AI 原生系统的七个核心部件

### 7.1 目标

系统首先要知道用户想完成什么，而不只是收到一句提示词。目标应包含成功条件、限制、时间和允许的操作范围。

### 7.2 上下文

模型需要的可能是当前页面、用户历史、企业知识、文件、数据库记录和实时状态。上下文不是越多越好，而是要与当前任务相关、可信并且有权限读取。

如果需要从大量私有资料中寻找信息，可以继续学习 [RAG 的基本原理](../../ai-advanced/rag-introduction/)。

### 7.3 模型

不同模型在推理、代码、视觉、语音、速度和价格上各有特点。AI 原生创作者不会把整个产品赌在一句固定提示词上，而会为任务选择合适模型，并准备超时、降级和替代路径。

### 7.4 工具

模型本身只能生成内容；要查询订单、写入数据库、发送消息或修改文件，就要通过工具调用进入真实世界。

每个工具都应有明确输入、输出、权限和幂等规则。删除、付款、发送和公开发布等高风险操作，不能因为模型“觉得应该做”就直接执行。

### 7.5 工作流与状态

复杂任务往往不止一次模型调用。系统需要知道已经完成什么、下一步是什么、失败后从哪里恢复，以及什么时候结束。

需要多步骤、分支、重试和人工确认时，可以继续学习 [LangGraph 工作流与高级 RAG](../../ai-advanced/langgraph-advanced-rag/)。

### 7.6 人的确认

AI 原生不是把人移出流程，而是把人的注意力放到最有价值的节点。

草稿生成可以自动完成；发送邮件、提交付款、删除数据、发布内容和修改生产环境，应根据风险提供预览、差异、撤销或明确确认。

### 7.7 评估与护栏

普通程序可以断言 `2 + 2 = 4`，生成式 AI 的输出却可能每次不同。你需要一组真实任务样本来判断：

- 结果是否正确、完整且可引用；
- 工具是否选择正确，参数是否安全；
- 不确定时是否会询问，而不是编造；
- 不同用户和语言下是否保持质量；
- 延迟和单次成本是否在预算内；
- 模型或提示词更新后是否发生退化。

没有评估集的 AI 产品，每次换模型都像在蒙着眼睛发布。

## 8. 从程序开发者到 AI 原生创作者

“AI 原生创作者”不只是一个新的程序员称呼。这个角色把产品、设计、工程、内容和智能系统编排到一起。

你的工作重心会发生这些变化：

| 过去主要关注 | 现在还要关注 |
| --- | --- |
| 写出正确代码 | 定义目标、边界和验收标准 |
| 设计固定页面流程 | 设计人、模型和工具怎样协作 |
| 测试确定性输入输出 | 建立真实案例与 AI 评估集 |
| Debug 某一行代码 | 追踪上下文、模型决策和工具调用 |
| 优化 CPU、内存和接口 | 同时优化质量、延迟与模型成本 |
| 发布一个版本 | 观察反馈，并持续调整模型与工作流 |
| 自己完成所有细节 | 调度 AI、现成能力和合作伙伴完成作品 |

你不必先成为全栈专家、设计专家和机器学习研究员才有资格开始。你需要的是逐渐建立系统判断：哪些问题交给普通代码，哪些交给模型，哪些必须由人决定，以及怎样验证最终结果。

## 9. AI 也改变了“创造产品”的过程

AI 原生不只发生在产品运行时，也发生在创作者的工作方式中。

### 想法阶段

让 AI 帮你整理访谈、比较现有方案、找出假设和反例，但不要让它替你证明用户真实存在。

### 设计阶段

让 AI 快速生成信息架构、线框图、视觉方向和交互原型，再让真实用户完成任务。好看的截图不能代替可用性验证。

### 开发阶段

先写清楚目标、边界和验收标准，再让 AI 分解任务、生成代码和补测试。一次只验证一个闭环，避免在无法运行的基础上同时增加十个功能。

### 测试阶段

除了单元测试和端到端测试，还要准备 AI 任务集：正常案例、边界案例、恶意输入、工具失败和需要人工确认的案例。

### 发布与运营阶段

AI 可以帮助生成发布说明、帮助文档、客服草稿和日志摘要，但隐私申报、价格承诺、审核回复和生产变更仍需要负责人确认。

AI 的价值不是替你按下所有按钮，而是扩大一个人的探索和交付能力，同时保留可验证的控制权。

## 10. 用同一个想法走完三次跃迁

假设你想帮助小团队整理会议后的行动项。

### 第一版：会议总结网页

用户看到一个介绍页面，可以粘贴一段文字并查看演示结果。

你验证的是：页面表达是否清楚，用户是否理解这个想法。

### 第二版：会议跟进程序

用户可以登录、上传记录、保存会议、编辑待办、分配负责人、导出结果；数据在不同设备间同步，失败可以重试。

你验证的是：这条任务链路是否真的节省时间，用户是否会重复使用。

### 第三版：AI 原生会议执行助手

用户给出“把这次会议推进下去”的目标。系统读取有权限的会议资料和项目状态，识别承诺与风险，询问含糊的负责人或日期，调用任务系统创建草稿，在发送通知前让人确认，并根据后续状态持续提醒。

你验证的是：AI 能否在真实约束中完成结果，而不只是生成一篇看起来合理的总结。

三版可能共享同一个界面和后端，但产品价值发生了变化：

```text
让用户看见信息
      ↓
让用户操作软件完成任务
      ↓
让用户把一部分任务交给软件完成
```

这就是从网页、程序到 AI 原生产品最重要的跃迁。

## 11. 一条适合初学者的作品路线

不要一开始就做“全自动通用 Agent”。用三个连续作品建立能力会更稳。

### 作品一：能公开访问的网页

目标：把一个想法清楚地展示出来。

至少包含真实内容、响应式布局、一个有效交互、基础无障碍和公开部署链接。

### 作品二：能长期使用的程序

目标：让用户完成一条有数据保存的真实任务。

至少包含前端、服务端、数据、身份或明确的访问边界、错误处理、Release 测试和发布流程。

### 作品三：有边界的 AI 原生产品

目标：让 AI 在一个具体领域中理解目标、使用上下文并调用至少一个受控工具。

至少包含结构化输出、工具权限、失败恢复、人工确认、十几到几十条真实评估案例，以及质量、延迟和成本记录。

完成第三个作品时，你不一定写了最多代码，却已经开始像产品设计者、系统工程师和 AI 编排者一样思考。

## 12. 五个常见误区

### “网页不是真正的程序”

错误。很多复杂产品本来就运行在浏览器中。这里的区别是静态原型与可靠系统，不是 Web 与原生谁更高级。

### “页面越多，越像完整产品”

页面数量不能代替任务闭环。一个只有三个页面但能可靠解决问题的工具，比拥有三十个空页面的模板更完整。

### “调用了大模型，就是 AI 原生”

一次文本生成只是能力接入。AI 原生还需要上下文、工具、状态、风险边界、人工确认和评估。

### “有了 Agent，就不需要后端”

恰恰相反。Agent 要访问真实数据和工具，更需要身份、权限、审计、限流、密钥保护和故障恢复。

### “AI 原生创作者不用懂技术”

你不必手写所有代码，但必须理解系统边界，能够验证 AI 的产物，并对用户、数据和发布结果负责。

## 13. 你现在处在哪一层

可以用下面的问题判断下一步，而不是追逐最新工具。

### 如果你还没有公开链接

先完成一个小网页，学会修改、部署和分享。此时不要急着加入登录、支付和 Agent。

### 如果你有很多漂亮 Demo

选一个最有价值的 Demo，补齐后端、数据、失败处理和真实发布，让陌生用户完成一次任务。

### 如果你已经能做完整程序

不要在所有页面加入聊天框。选择一个过去必须由人理解和判断的步骤，把它改造成有上下文、有工具、有确认、有评估的 AI 工作流。

### 如果你已经做了 AI 功能

检查它是否真的改善任务结果。建立评估集，记录错误、延迟、成本和人工接管率，再决定是否增加自主性。

## 14. 最后的成长检查表

### 从网页到程序

- [ ] 产品不依赖开发者电脑也能运行；
- [ ] 数据、权限和密钥有正确边界；
- [ ] 用户能完成端到端任务；
- [ ] 失败、升级、监控和恢复已经设计；
- [ ] 有适合目标用户的平台和发布方式。

### 从程序到 AI 原生产品

- [ ] AI 解决的是核心任务，而不是装饰功能；
- [ ] 上下文来源明确，并经过权限检查；
- [ ] 工具调用有结构化输入、限制和审计；
- [ ] 高风险动作需要人确认或可以撤销；
- [ ] 失败时可以重试、降级或交还给人；
- [ ] 有真实评估案例，而不是只测试一个提示词；
- [ ] 能观察质量、延迟、成本与用户结果。

### 从开发者到 AI 原生创作者

- [ ] 我先定义问题、目标和验收标准，再生成代码；
- [ ] 我能判断普通代码、AI 和人各自应该负责什么；
- [ ] 我会组合模型、数据、工具和现有平台，而不是什么都重造；
- [ ] 我把 AI 产物当作需要验证的候选方案；
- [ ] 我对隐私、安全、发布和用户承诺承担最终责任。

最开始，你让 AI 帮你做出一个网页；然后，你学会让网页背后拥有数据、服务和可靠运行的系统；最后，你开始设计一种新的软件——它能理解目标、使用工具、与人协作，并在真实世界中交付结果。

当你走到这里，你创造的已经不只是页面或代码。你在编排界面、程序、数据、模型和人的判断，把一个想法变成真正能够工作的智能产品。这就是 AI 原生创作者。
